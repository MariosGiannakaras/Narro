**A2 — one serialized timeline with renderer/native frame ownership.** Target 500 ms nominal total and an easing with soft start/end, no bounce; use one authoritative monotonic elapsed progress (rather than independent, drifting 250/270/500 ms waits). Shared task title, displayed timer, action targets and subtask summary retain semantic identity while their *visual representatives* move to destination anchors. **A3 — lifecycle and reversibility.** Route transitions through a state machine: IDLE, PREPARING, ANIMATING, COMMITTING, ROLLING_BACK. Define deterministic failure/timeout cleanup for prepaint, IPC, DWM/region placement, watchdog and navigation; never leave an invisible but input-blocking overlay, orphaned bitmap hold or stale accessible content. ## Track B — one persistent window for whole app, after all M1–M9 are accepted

**B0 — explicit feasibility gate before a single code change.** Audit real product behavior: can the Main workspace and a detached, always-on-top Floating Timer be visible **simultaneously** or on separate monitors? One single HWND cannot independently position, z-order and show *two physically separate surfaces* at once. If such co-visibility is required, strict one-HWND parity is impossible without changing the interaction model; choose and document a user-approved alternative *before migration*: (a) single visible surface at a time with a compact timer docked inside Main while it is active and floating when Main is not shown; or (b) preserve the two-window architecture where independent co-visibility is essential. Do not silently discard an existing capability to achieve a window-count metric.

**B1 — target owner/architecture.** One persistent Tauri top-level main/focus host and one WebView/root, with `Main`, `Focus Panel`, `Compact Timer`, `Expanded Timer` as orchestrated presentations under one serial native/React presentation owner. Keep Rust timer/session + SQLite authority and event ordering, and preserve board/report/editor/notification/tray persistence. Analyze host sizing to accommodate the maximum Main (dynamic resize/maximized/fullscreen/work area), not only 1000 x 700 defaults. Use DPI-aware native regions/position for 340-pixel Focus and Timer visible bounds. Avoid full-host WebView resize per animation frame if it causes recompose/flicker; benchmark viable one-HWND alternatives. A native helper popup during animation must be specifically reviewed against the intended *strict one-HWND* requirement; do not claim literal one HWND if one is used.

**B2 — Main/window chrome contract.** Main currently has native Windows titlebar and can be moved/resized/maximized; Focus/Timer are borderless. Compare solutions for stable caption handling: a reversible native decorations style transition (risk: non-client flicker, taskbar/snap) vs one borderless host with a source-matched accessible custom caption *only when showing Main*. Do not choose by aesthetics alone; physical tests must preserve actual Main close/minimize/maximize/resize/drag/snap/keyboard/assistive technology and taskbar semantics, and Focus's borderless shape. Retain the current approved Main appearance as closely as possible; request explicit user product decision only if an unavoidably visible or behavioral tradeoff remains.

**B3 — design new Main animations, consistent with Motion v4 (not yet implemented).**

| Journey | Nominal motion design | Content order |
| --- | --- | --- |
| Main -> Focus Panel via Blitz now | 500 ms one-window position/visible-extent morph from **actual** Main rect/monitor (including restored/maximized variants) to intended Focus edge; same easing and one time owner as Motion v4 | Freeze/recede planning surface, preserve the chosen live-task identity/title at the handoff anchor if present, reveal Focus live card/header/queue only after there is space; no blank transient |

| Main ↔ Compact/Expanded Timer, if a direct route exists | 500 ms morph using current Timer placement (not fabricated centered coordinates), passing only through logically valid presentation states | Keep active timer/session uninterrupted; controls and subtasks use Motion v4 reveal/retract choreography; avoid auto-start |
| Internal Main navigation | Keep current native Main layout/interactions; unrelated tabs/modals do **not** inherit a 500 ms window animation | Only short existing UI micro-motion where appropriate |

If a title/card cannot be matched between two real views, transition a single stable semantic anchor and fade the rest; do **not** invent a flying task card. Treat 500 ms as the approved *product target*, not a claim about measured Blitzit. The tutorial source shows only ~270 ms on Panel -> Timer; Main animations are Narro-local proposals.

**B4 — Main UI prototype and canonical fixtures.** First create a separately navigable interactive Main -> Panel -> Compact -> Expanded -> Compact -> Panel -> Main HTML/React visual prototype from **actual current Main/Focus components and UI assets**, not arbitrary mock layouts; submit 500 ms normal/reduced, reverse, restored/maximized and multiple-monitor variants for user visual approval. **B5 — incremental migration rather than big-bang rewrite.** Introduce serial Main/Focus presentation state and in-place prepainting before removing a window; bridge existing Main navigation, timer projection, focus shortcut routing, tray/show/recreate calls, topmost policies, drag placement and accessibility. Remove obsolete second host, cross-window events and capabilities **only after** end-to-end evidence proves no dependent consumer remains. No arbitrary changes to data schema, registered shortcuts, coloring or icon picker.

**B6 — validation and release baseline.** Source/fixture/contract tests and prescribed CI at each reviewable slice; native physical pass for Main↔Panel and required Main↔Timer journeys normal/reduced (at least 4 Main↔Panel cases accounting for entry and return, plus all relevant routes), 60 fps compositor frame-by-frame, focus/keyboard/UIA, multi-monitor, DPI 100/125/150/200%, Win key snapping, maximize/restore, Alt+Tab/taskbar, tray reopen/quit/startup, click-through, drag, long-running timer, DB/session durability, crash rollback, and idle CPU/RAM. Reopen precisely affected M1/M5/M6/M7/M8/M9 acceptance claims and obtain replacement-code acceptance on resulting main **before** entering M10.
