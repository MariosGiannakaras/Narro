**Current Narro:** PR298 (merged `2f0620295ff4588163e6bbf2e57b9fd1475bfa15`) introduced `TimezonePreferenceSelector.tsx`: native accessible select, Dynamic `Intl.supportedValuesOf('timeZone')` catalog, Automatic Windows fallback, existing saved zones and validated `Other IANA timezone` draft with Escape/Cancel/Enter; `timezoneSelection.ts` renders `GMT±hh:mm` using `Intl.DateTimeFormat` at the chosen instant and saves **bare IANA** IDs. `scripts/test-timezone-selection.mjs` explicitly tests Athens `GMT+03:00` summer/`GMT+02:00` winter, UTC, Kathmandu +05:45 and invalid zones. Existing typed preference patch/SQLite restores prior value on failed frontend save.

**Narro-only code-level validation observation relevant to source uncertainty:** `src-tauri/src/preference_settings.rs::prepare_patch` does **not** validate `patch.timezone` against IANA rules; `apply_patch` trims and stores it; `src-tauri/src/persistence/preferences.rs::validate_preferences` only applies `validate_optional_token` to the timezone, unlike the frontend's `isValidIanaTimezone` check. It is a **source-independent potential input-validation defect**, not evidence of Blitzit behavior, a demonstrated crash or a tested exploit. Requiring valid IANA is already Narro's stated policy, so a later technical validation hardening can be scoped without guessing source dropdown logic; any data migration/changed semantics for historically stored invalid identifiers must preserve scheduling/report invariants and be separately reviewed. **No code change in this audit; no new tests run.**

**Disposition:** `BLITZIT_CONFIRMED_LABEL / NARRO_INFERRED_IMPLEMENTED / SOURCE_MENU_D​ST_UNKNOWN / VALIDATION_GAP_CODE_OBSERVED`.
