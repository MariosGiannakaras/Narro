But neither the structural JS contracts nor Rust bitmap arithmetic tests can observe actual Windows DWM/WebView2 layer ordering and old cached pixels. This is the same acceptance family as the verified 4/8 failure and needs the new 8-case original desktop evidence.
2. **HIGH — popup/host position non-atomicity.** `animate_focus_surface_presentation_internal` presents each bitmap then calls `set_focus_position`; `focus_webview::set_physical_position` calls owner `set_position`, then separately `sync_owner_position` on the owned popup, then schedules WebView2 `NotifyParentWindowPositionChanged`. The correction eliminates known 50ms eventual-sync drift and propagates popup-sync failures, but this is still **sequential movement of two HWNDs**, not a proved atomic DWM commit. Native cross-monitor movement/100–125%/edge/high-motion frames are required; do not assert a currently observed misalignment.
3. **HIGH — final screen ownership versus renderer paint receipts.** Two-rAF deadline waits, `CapturePreview` and final PNG decode guarantee bounded ordering and image arithmetic, **not** that the compositor has presented those exact pixels. The documented previous FAIL survived green capture/DOM readiness receipts. A native 60fps frame-by-frame review is the acceptance instrument.
4. **MEDIUM — partial-failure reconciliation.** `commitPreparedFocusPresentation`/Timer protected resize cover many rejection/rollback paths and `FOCUS_MODE_RASTER` has token and watchdog. However simulated-ops and string-contract tests do not jointly exercise actual Win32 `SetWindowPos`, `UpdateLayeredWindow`, `DestroyWindow` and asynchronous WebView2 notification failure while the renderer is still transitioning. The coordinator's error catch also publishes the previous renderer view even if its native recovery returned an error; the native watchdog is a fallback, not immediate proof of visual coherence. Check failure injection/rapid interaction and overlay cleanup on the exact native candidate before claiming this family closed.
5. **MEDIUM — fresh expanded content generation.** The subtask-loading marker and 1500ms bounded wait fix a real early capture of loading text and the create-input pop-in path. They do not prove all task/list mutation invalidations, asynchronous render ordering or tooltip/pointer occlusions on actual native WebView2 are covered.
