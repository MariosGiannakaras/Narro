## Process attribution

Last-snapshot breakdown across the three runs:

- WebView2 working set: approximately 362.05–369.12 MiB;
- `narro.exe` working set: approximately 32.5 MiB;
- WebView2 private bytes: approximately 259.58–277.02 MiB;
- `narro.exe` private bytes: approximately 60.4 MiB.

The memory footprint is therefore dominated by WebView2 rather than the Rust host.

Summed working set includes shared/resident pages across processes and is not equivalent to unique physical RAM, so private bytes are retained as the companion allocation metric.

## Stability interpretation

Idle CPU is effectively zero. The measured scaffold does not show evidence of an unexplained polling loop or continuous animation workload.

Run 2 shows a one-time WebView2 private-memory allocation increase. Run 3 then stabilizes at about 337.17 MiB average private bytes with only about 0.13 MiB min-to-max movement over the full minute. This does not establish a continuing memory leak; it establishes a warm-state baseline to compare with later repeated Focus↔Floating and Notes/subtask expansion stress tests.

## Decision

**Proceed with the current Tauri + WebView2 `focusSurface` architecture.**

Reasoning:

- idle CPU is near zero;
- all three process trees are stable;
- the final warm run plateaus rather than continuing to grow;
- the repository intentionally has no arbitrary RAM pass/fail threshold;
- `docs/DECISION_GATES.md` explicitly says not to use an arbitrary RAM target as the sole gate criterion;
- current evidence does not justify the complexity of a native Win32/WinUI Floating Timer rewrite.

Revisit performance after the real Floating Timer UI exists. Required later comparison includes collapsed idle, expanded idle, timer-running CPU, and memory before/after repeated Focus↔Floating and Notes/subtask expansion stress tests.
