# 2026-10-10 — Pre-Codex audit A04: repeated Main/Focus task mutations before React pending state publishes

## Exact source evidence
Live main at first inspection `86b9c5b37d99585b31227906e93d14c473ccdeab` (docs advanced later; recheck before implementation). `src/ListBoard.tsx` `submitCreate` checks `editorMutationPending` from React render state, validates input, invokes `setEditorMutationPending(true)` then `await createListBoardTask(...)`; no synchronous in-flight ref. The endpoint creates a fresh task ID. Two same-render user interactions (e.g. Enter and click) can both pass and create two separate task IDs before React publishes busy=true; this is a provable renderer-side race risk, not evidence that an actual live duplicate occurred. `ListBoard` already applies explicit synchronous refs for destructive delete, quick schedule removal and recurring removal, demonstrating the local established prevention convention and a narrow implementation path. `duplicateTaskFromBoard` similarly uses state-only `mutationPendingTaskId` before `await duplicateListBoardTask` and has independent double-duplicate risk.

`src/FocusPanel.tsx` likewise has `submitAddTask` (`addTaskPending`), `commitRowMutation` (`mutationPendingTaskId`), `confirmDelete` (`deletePending`), `makeTaskLive`, `confirmTaskChangeList` etc with state-only guards. Their authoritative Rust commands have different idempotence/failure characteristics; never infer all are equally vulnerable without classifying each command. `FocusLiveActions` live timer actions are a *separate* first slice in audit PR305: synchronous action gate for Done/Skip/Pause/Extend/Break, CI initially pending, no Main Board change.
