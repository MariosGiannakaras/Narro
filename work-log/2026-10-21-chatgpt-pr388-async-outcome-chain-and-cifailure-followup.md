## Deeper C44 async ownership: real production defect discovered after CI
The existing source/recording fixed popover unmount by separating `saving` from `disabled`, but the initial test harness used a `Promise<boolean>` directly in `SoundPreferenceControl` while the **production chain discarded it**.

Actual call chain examined end to end:
1. `SoundPreferenceControl` range `onKeyUp`/pointer → `commitVolume()` sets `submittedVolume`/in-flight ref; `await onVolumeCommit(next)`; when native returns false, it resets draft and submission; when rejected, it displays an error.
2. `PreferenceSettingsSections.tsx`: each alert/notification/success volume callback **returns** `onSave({ taskAlertVolumePercent }, "taskAlertVolume")`, equivalent for other two volumes.
3. `ThemeSettingsPanelContent` defined an `onSave` adapter as `{ void preferences.save(patch,key); }`, i.e. returned **undefined immediately**. Therefore `await onVolumeCommit()` at #1 did not actually await the IPC write, could not see the false outcome, and released the per-component guard before the native request settled. Success/rejection could appear indistinguishable to the component; native provider error remained separate.
4. `PreferenceSettingsRuntimeProvider.save` does await `updatePreferenceSettings` and returns true/false, re-fetching authoritative preferences on native failure. In this campaign, a **synchronous `useRef` single-flight guard** was already added to reject cross-family/same-event-turn competing save requests before React `pendingKey` rerender, and release only after success or recovery.

**Causal correction:** `ThemeSettingsPanelContent.save` now returns `preferences.save(patch,key)` *without a void wrapper*. Type `CommonProps.onSave` already supported `void | Promise<boolean>`; no change in Rust IPC, DB, timer/session, preference schema, UI layout or parent toggle semantics. `SoundPreferenceControl` now receives the authoritative result, holds in-flight admission until it settles, and can roll back draft on false. `scripts/test-ui-preferences.mjs` asserts non-void production call-chain preservation. An isolated direct execution of the actual fetched production save-adapter body with a fake provider returning `Promise<false>` confirmed the Promise and false propagate end to end (scoped PASS).

**First failing test diagnosis:** the extended mock `scripts/test-sound-preference-save-focus.mjs` released the original successful promise, awaited that *inner* promise and one microtask, then immediately tried a new save. That does not prove the *outer async `commitVolume` `finally`* has run; the single-flight guard correctly suppressed the new attempt and the draft remained75. The test had unintentionally interpreted a refused overlapping request as a tested save rejection. We preserved the rollback assertion and added an event-loop-turn microtask flush via `setImmediate` in the test harness **after the prior promise/after each rejected or thrown mock call**, and explicit counters asserting the rejected/throwing onVolumeCommit was invoked **exactly once**. No artificial delay or renderer wait was inserted into production.
