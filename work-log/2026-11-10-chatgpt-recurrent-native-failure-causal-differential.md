## Newly established deterministic defect: timed-out queued GUI operation is not cancelled

**Before correction** in PR499's inherited `src-tauri/src/main_focus_raster.rs`, `on_window_thread` dispatched `operation()` with `run_on_main_thread` and then called `receive.recv_timeout(Duration::from_secs(2))`. After timeout, the UI closure remained scheduled and could still execute. In `Raster::begin`, a late closure can create and show an unowned `NarroBoardFocusPixels` popup **after** the caller has reported failure and used the direct Focus fallback. The popup's 8s watchdog bounds its lifetime, but not the wrong transient user-visible overlay. This is a provable source-level interleaving, **not proof it was the cause of the PR437 original frame**. `set_rect` and `release` dispatches also share the timeout boundary.

**Fix on the existing PR499 branch:** commit `cc7122eb6770de2a3b2f9a1d4f59b62f5d855b12` adds `UiDispatchPermit` as an atomic three-state queued(0)/started(1)/cancelled(2) admission guard. The queued GUI closure must `try_start()` before invoking the native operation. On receiver timeout, `cancel_if_queued()` prevents a later queued operation from starting; if already started, the error explicitly reports that completion is uncertain and leaves the existing native/watchdog error path intact. It does **not** attempt to cancel an already running GUI action unsafely. Two Rust regression tests exercise timeout-before-start and start-before-timeout control ordering. This is one Rust source-file change, no persistence schema, CSS, renderer, product preference or native movement design change.
